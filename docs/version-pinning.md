# Version pinning

The Monolith's reproducibility guarantee rests on pinned build inputs.
Build inputs are pinned by two decoupled epochs — `TOOLCHAIN_EPOCH` (the
builder image) and `BUILD_EPOCH` (the runtime portage snapshot) — each
driving its own lock file. This document explains the two-pin model, the
pin layers each epoch drives, how the automated bump pipeline works, and
what to do when a bump breaks the build.

## The two-pin model

Two independent epochs pin the build. They used to be a single date
(`BUILD_EPOCH` pinned the stage3 base image *and* the runtime portage
snapshot together, "always equal"); they are now deliberately decoupled so
that a pruned or self-hosted runtime snapshot never forces a builder-image
rebuild, and vice versa.

### `TOOLCHAIN_EPOCH` — pins the builder image

`ARG TOOLCHAIN_EPOCH` in the `Dockerfile` pins the
`gentoo/stage3:amd64-openrc-<date>` base image *and* the portage tree baked
into the image to resolve host build tools and the crossdev toolchain
(`emerge-webrsync --revert=${TOOLCHAIN_EPOCH}`). It drives:

- `configs/portage/crossdev.lock` — the `sys-libs/musl` / `sys-devel/gcc`
  `CROSS_*_VER` pins passed to `crossdev --libc` / `--gcc`
- the registry image tags (`make push-image` tags both the main image and
  the `-base-tools` image `:$(TOOLCHAIN_EPOCH)`)

`TOOLCHAIN_EPOCH` is bumped **rarely and deliberately**. Changing it rebuilds
the entire builder image (`make build-image`) — comparatively slow, and
consequential enough that a new musl/gcc pin can break the cross-toolchain
build (see "When a bump breaks the build" below). There is no dedicated
"toolchain-bump" automation yet: today, bumping `TOOLCHAIN_EPOCH` is a
manual `Dockerfile` edit, followed by `make build-image` and a `crossdev.lock`
regeneration (`update_crossdev_lock()` inside `scripts/update-build-pins.sh`,
currently only invoked as a side effect of a `BUILD_EPOCH` bump — see
"Deferred follow-ups").

### `BUILD_EPOCH` — pins the runtime portage snapshot

`ARG BUILD_EPOCH` pins the portage snapshot used to resolve *target*-package
versions for the ISO — the tree `configs/portage/versions.lock` is generated
against. It is **not** baked into the builder image. `scripts/sync-portage.sh`
injects it at build time (`make sync-portage`) into the `monolith-repos`
Docker volume, self-hosted on S3 (`s3://$S3_BUCKET/portage-snapshots/`)
rather than pulled fresh from `distfiles.gentoo.org` every time:
`sync-portage.sh` tries our S3 mirror first, falls back to the upstream
Gentoo snapshot server on a miss, and archives whatever it fetches back to
S3 for next time. This makes runtime-snapshot bumps immune to Gentoo mirror
pruning (a snapshot fetched once stays available on our bucket even after
upstream rotates it out of `distfiles.gentoo.org`) and, since it never
touches the builder image, cheap: no image rebuild. `BUILD_EPOCH` drives:

- `configs/portage/versions.lock` (`make update-versions`, see below)
- `ENV SOURCE_DATE_EPOCH` in the `Dockerfile` (kept equal to `BUILD_EPOCH`
  at midnight UTC, for reproducible build-output timestamps)

`BUILD_EPOCH` is bumped **routinely and cheaply** — it's the pin meant to
move often.

### Which command regenerates which lock

| Lock file | Epoch | Regenerated by |
| --- | --- | --- |
| `configs/portage/versions.lock` | `BUILD_EPOCH` | `make update-versions` — regenerates against the runtime snapshot `make sync-portage` fetches into the `monolith-repos` volume (`update-versions` now depends on `sync-portage`; see the Makefile comment above that target) |
| `configs/portage/crossdev.lock` | `TOOLCHAIN_EPOCH` | the toolchain flow — today, `update_crossdev_lock()` inside `scripts/update-build-pins.sh`, which queries whichever `monolith-builder` image is currently built locally (that image is keyed on `TOOLCHAIN_EPOCH` as of the two-pin split) |

### Deferred follow-ups

- **Self-hosting the toolchain-image inputs (stage3 base *and* its baked
  portage tree).** Only the *runtime* portage snapshot (`BUILD_EPOCH`, via
  `sync-portage.sh`) is self-hosted on S3 today. Two toolchain-image inputs
  remain pulled straight from upstream on a `TOOLCHAIN_EPOCH` rebuild, both
  exposed to the same upstream pruning the runtime snapshot used to be:
  1. the `gentoo/stage3:amd64-openrc-<TOOLCHAIN_EPOCH>` base image from
     Docker Hub (`FROM …` in the Dockerfile); and
  2. the portage tree baked into `base-tools` via the Dockerfile's
     `emerge-webrsync --revert=${TOOLCHAIN_EPOCH}` — this is a **plain
     upstream fetch with no S3-first fallback** (`sync-portage.sh`'s
     resilient path is wired only into the runtime `make sync-portage`
     step, not the image build).

  In practice this is dampened because the built image is cached in our
  GHCR and `TOOLCHAIN_EPOCH` bumps are rare and human-gated, so a cold
  rebuild that actually re-hits upstream is uncommon — but a GHCR
  eviction, a forced older `TOOLCHAIN_EPOCH`, or a local-dev rebuild will
  hit it directly, and Success Criterion "builds never fail from upstream
  pruning" therefore holds only for the runtime snapshot, not the
  toolchain image. Also note `TOOLCHAIN_EPOCH` must land on a date that has
  a *published* `gentoo/stage3` tag — those are cut ~weekly (Mondays),
  unlike the daily portage snapshots, so it will usually lag `BUILD_EPOCH`.
  Mirroring both stage3 tarballs and the toolchain tree the way
  `sync-portage.sh` mirrors runtime snapshots is a planned follow-up.
- **A scheduled `TOOLCHAIN_EPOCH` cadence.** `BUILD_EPOCH` bumps are cheap
  enough to run on a schedule (weekly, via `pin-bump.yml`); `TOOLCHAIN_EPOCH`
  bumps are not (full image rebuild + validation), and there is no dedicated
  bump command or workflow for it yet at all — see the previous section. A
  proper toolchain-bump flow, with a maintenance cadence looser than the
  weekly snapshot bump (e.g. monthly, `workflow_dispatch`-gated to start),
  is a planned follow-up.

## The three pin layers

All three files are checked into git and are the actual source of truth —
this document explains them, it doesn't define them.

### 1. `Dockerfile` — `ARG TOOLCHAIN_EPOCH` + `ARG BUILD_EPOCH` / `ENV SOURCE_DATE_EPOCH`

```dockerfile
ARG TOOLCHAIN_EPOCH=20260811
ARG BUILD_EPOCH=20260811
FROM gentoo/stage3:amd64-openrc-${TOOLCHAIN_EPOCH} AS base-tools
...
ENV SOURCE_DATE_EPOCH=1786406400   # == BUILD_EPOCH at midnight UTC
...
RUN emerge-webrsync --revert=${TOOLCHAIN_EPOCH}   # baked toolchain tree, NOT the runtime one
```

Two independent `YYYYMMDD` dates, per "The two-pin model" above:

- `TOOLCHAIN_EPOCH` pins the `gentoo/stage3:amd64-openrc-<date>` base image
  *and* the portage tree baked into the image
  (`emerge-webrsync --revert=${TOOLCHAIN_EPOCH}`), used only to resolve host
  build tools and the crossdev toolchain.
- `BUILD_EPOCH` pins the runtime portage snapshot — not baked into the
  image at all; injected separately by `scripts/sync-portage.sh`
  (`make sync-portage`). `SOURCE_DATE_EPOCH` is `BUILD_EPOCH` expressed as a
  Unix timestamp; it clamps build output timestamps for reproducibility
  against the runtime snapshot date and is always kept equal to it.

Prior to the two-pin split these were a single date (`BUILD_EPOCH` pinned
both the stage3 image and the portage snapshot together, "always equal").
They're now decoupled on purpose — see "The two-pin model" above for why.
**Each is its own master lever** for the pin layers it drives (`crossdev.lock`
for `TOOLCHAIN_EPOCH`; `versions.lock` for `BUILD_EPOCH`); neither implies
the other.

`BUILD_EPOCH` is managed by `scripts/update-build-pins.sh` (`check` /
`update`), which runs entirely on the **host** (`curl` + `python3`, no
Docker required). `update` queries Docker Hub for the latest
`amd64-openrc-YYYYMMDD` tag and — this is the important safety check —
verifies a matching portage snapshot (and its GPG signature) actually
exists on `distfiles.gentoo.org` *before* writing the new date into the
Dockerfile. A stage3 image can exist for a date before its matching
snapshot does; `update` refuses to pin to that date until both exist. (This
still uses the stage3 tag as its freshness signal even though `BUILD_EPOCH`
no longer pins stage3 — reworking `update-build-pins.sh` to source dates
independently for each epoch, and to add a dedicated `TOOLCHAIN_EPOCH`
update path, is part of the deferred toolchain-bump-flow follow-up above.)
There is currently no equivalent `check`/`update` command for
`TOOLCHAIN_EPOCH`; bumping it is a manual `Dockerfile` edit.

```sh
scripts/update-build-pins.sh check              # show current vs. latest (BUILD_EPOCH)
scripts/update-build-pins.sh update              # bump BUILD_EPOCH to latest verified date
scripts/update-build-pins.sh update 20260727     # force a specific date (still verified)
```

### 2. `configs/portage/versions.lock` — world package versions

71 world packages (`configs/portage/world`), pinned as
`category/package:version:slot`. Regenerated by
`scripts/update-versions.sh update`, which runs **inside the built
container** and asks portage itself (`portageq best_visible`) what the best
visible version of each world package is — i.e. what `BUILD_EPOCH`'s
portage snapshot actually offers.

```sh
make update-versions     # runs inside monolith-builder
```

This queries the portage tree in the `monolith-repos` Docker volume, not
anything baked into the image. Since the two-pin split, that volume is
populated at the current `BUILD_EPOCH` by `scripts/sync-portage.sh`
(`make sync-portage`) — **not** by `make build-image`, which only rebuilds
the toolchain at `TOOLCHAIN_EPOCH` and no longer touches the runtime
snapshot at all. `update-versions` depends on `sync-portage` in the
Makefile precisely so `make update-versions` always fetches the current
`BUILD_EPOCH` snapshot first; you don't need to (and rebuilding the image
wouldn't help you) run `make build-image` before this for a `BUILD_EPOCH`
bump.

### 3. `configs/portage/crossdev.lock` — musl + gcc cross-toolchain pins

Just two lines: `sys-libs/musl` and `sys-devel/gcc`, in the same
`category/package:version:slot` format. These are cross-toolchain-specific
(passed to `crossdev --libc` / `--gcc`) and aren't a "world" package, so
they're pinned separately from `versions.lock`. `binutils` *is* a world
package and lives in `versions.lock`; `linux-headers` is derived at build
time from the kernel version's major.minor (see `Makefile`).

Regenerated by `update_crossdev_lock()` inside
`scripts/update-build-pins.sh`, via `docker run <builder-image> portageq`
— i.e. it queries whatever `monolith-builder` image is *currently present
locally*, which (since the two-pin split) is the image built at
`TOOLCHAIN_EPOCH`, not `BUILD_EPOCH`.

**Important quirk, by design:** today, `update_crossdev_lock()` is only
invoked as a side effect of `update-build-pins.sh update` — which bumps
`BUILD_EPOCH`, not `TOOLCHAIN_EPOCH`. So on an ordinary (`BUILD_EPOCH`-only)
weekly bump, this regeneration just re-queries the same already-built
`TOOLCHAIN_EPOCH` image and is a no-op (nothing to lag). The "lags by one
bump cycle" quirk described in the script's comments is about
`TOOLCHAIN_EPOCH` bumps specifically: if `TOOLCHAIN_EPOCH` changes and
`update_crossdev_lock()` runs *before* `make build-image` rebuilds the
image at the new epoch, it queries the **previous** epoch's image. This is
intentional (documented in the script) and is why the pipeline below builds
the image *twice* around a full pin bump: once (pre-bump) to seed
`crossdev.lock`'s query, and once (post-bump) to seed `versions.lock`'s. A
dedicated toolchain-bump flow that separates this from the `BUILD_EPOCH`
path cleanly is a planned follow-up (see "Deferred follow-ups" above).

## How the automation works

`.github/workflows/pin-bump.yml` runs weekly (Mondays 06:00 UTC — three
hours after `build.yml`'s own unrelated weekly build at 03:00 UTC, so this
workflow doesn't start touching pins while that run still has a warm cache)
and on manual `workflow_dispatch`, with an optional `target_epoch` input to
force a specific date instead of "latest available".

```
check (host, cheap)
  │  scripts/update-build-pins.sh check
  │  no-op + clear log if already current — job 2 doesn't even run
  ▼
bump-and-validate
  │  1. pull the current-epoch monolith-builder image (cache seed)
  │  2. scripts/update-build-pins.sh update [target_epoch]
  │       → bumps Dockerfile, regenerates crossdev.lock from the OLD image
  │  3. make build-image
  │       → rebuilds the toolchain at the NEW epoch
  │  4. make update-versions
  │       → regenerates versions.lock from the NEW image
  │  5. commit + push to pins/bump-<old>-<new>
  │  6. gh workflow run build.yml --ref pins/bump-<old>-<new>
  │       → runs the SAME build.yml used for every normal build/release:
  │         build-image, build (packages/rootfs/iso), attestation
  │         (SBOM + license + CVE gate — Pillar 3 of scripts/attestation.sh)
  │       → any job build.yml gains later (a dedicated CVE-gate job, a
  │         boot-test job) is included automatically — pin-bump.yml doesn't
  │         hardcode job names, it dispatches the whole workflow and reports
  │         every job's conclusion generically
  │  7. wait (bounded) for that run, gather per-job results
  ▼
gh pr create — labeled pin-bump + (validated | needs-fixup)
  never auto-merged; a human always approves
```

**Post-decoupling note:** this pipeline still bumps only `BUILD_EPOCH`
(`update-build-pins.sh update` doesn't touch `TOOLCHAIN_EPOCH`), so step 3's
`make build-image` is no longer "rebuild the toolchain at the NEW epoch" —
`TOOLCHAIN_EPOCH` hasn't changed, so it's a cheap no-op (see the `BASE_HASH`
note above the `build-image` Makefile target). Step 4's `make update-versions`
is still correct: it now fetches the runtime snapshot itself (`sync-portage`
prereq) rather than relying on step 3 having refreshed it. Splitting this
into a cheap, auto-mergeable `BUILD_EPOCH`-only flow (skipping the now-moot
`build-image` step entirely) and a separate human-gated `TOOLCHAIN_EPOCH`
flow is a planned follow-up.

If `make build-image` or `make update-versions` fails, the pipeline still
opens a PR (with whatever pins *did* get bumped) labeled `needs-fixup`, and
skips the full validation dispatch — there's no point burning CI minutes on
a build we already know is broken locally. If the full `build.yml`
dispatch fails (or times out — see below), the PR is opened labeled
`needs-fixup` with the per-job results and a link to the run. If everything
passes, the PR is labeled `validated`. **The bump is never merged
automatically in any of these cases** — a human reviews and merges.

### Why `build.yml` isn't called via `workflow_call`

The ideal end state is a `workflow_call`-reusable `build.yml` invoked
directly as a job dependency of `pin-bump.yml`, giving one literal build
definition with typed inputs/outputs instead of dispatch-and-poll. This
wasn't done here because `build.yml` is being actively edited by two other
in-flight branches (a CVE-gate job and a boot-test job) — touching it now
would create merge conflicts across three branches for no functional gain.
`gh workflow run build.yml --ref <branch>` + polling achieves the same
practical goal (exactly one build definition, reused as-is, always current)
without touching the file at all.

**Update:** `build.yml` briefly exposed a `workflow_call` trigger (added so
`release.yml` could reuse it), but it was **removed** — calling `build.yml`
from another workflow broke Sigstore attestation: GitHub binds the signing
certificate to the *entry* workflow, so `actions/attest@v2` failed to persist
with `values do not match: build.yml != release.yml`. `build.yml` now triggers
directly on release tags and `release.yml` publishes after it via
`workflow_run` (see `docs/releasing.md`). So the `workflow_call`-reusable
"ideal end state" described above is **not** available for anything that needs
to attest/sign under its own identity. `pin-bump.yml` doesn't sign — it only
validates — so it *could* dispatch `build.yml` however it likes; it still
dispatches-and-polls as described here, and that approach remains correct and
doesn't need to change.

### Wait budget

The `bump-and-validate` job has `timeout-minutes: 355` (GitHub-hosted
runners hard-cap a single job at 360 minutes regardless of this setting).
Roughly 100 minutes are budgeted for the local image rebuild + lock
regeneration, and 240 minutes for the bounded wait on the dispatched
`build.yml` run. These numbers are estimates — this repo's build is not run
on the authoring machine, so real timings should be observed from actual CI
runs and these budgets tuned accordingly. If the dispatched run doesn't
finish within its wait budget, the wait step reports `conclusion=timed_out`
rather than being silently killed; the PR is opened labeled `needs-fixup`
with a link to the (possibly still-running) validation run.

## Cadence and manual overrides

- **Automatic:** every Monday 06:00 UTC.
- **Manual, latest available:** Actions → "Pin Bump" → *Run workflow*, leave
  `target_epoch` empty.
- **Manual, forced date:** same, but set `target_epoch` to a specific
  `YYYYMMDD`. Still gated by the portage-snapshot-exists check inside
  `update-build-pins.sh`.
- **Fully manual / local, no CI (`BUILD_EPOCH` bump):**
  ```sh
  make update-build-pins   # bump Dockerfile BUILD_EPOCH + SOURCE_DATE_EPOCH
  make update-versions     # sync-portage (fetch new snapshot) + regenerate versions.lock
  ```
  `make update-versions` depends on `sync-portage` in the Makefile (see the
  comment above that target), so it always fetches the current `BUILD_EPOCH`
  snapshot before regenerating `versions.lock` — a `make build-image` step
  in between is **not** required for a `BUILD_EPOCH`-only bump, since the
  two-pin split: `build-image` only rebuilds at `TOOLCHAIN_EPOCH`, which
  this doesn't touch. Both `make update-all` (`update-build-pins` +
  `update-versions`) and `make bump-pins` (`update-build-pins` +
  `build-image` + `update-versions`) are now equally correct for this case;
  `bump-pins` just also tolerates a manually-bumped `TOOLCHAIN_EPOCH` in the
  same pass (its `build-image` step is a harmless no-op otherwise). Before
  the two-pin split, `update-all` and `bump-pins` differed in a way that
  mattered here — that historical distinction no longer applies.

## When a bump breaks the build (the fixup loop)

This has happened before — see the git history around `Update build epoch:
20260420` followed by `Fix musl build pins` and `Fix musl build pins 2`.
Bumping `BUILD_EPOCH` can shift package versions in ways that break the
cross-toolchain build (a new musl/gcc pin failing to build against the
kernel headers pin, a portage mask change, etc.). The automation's policy
mirrors what actually happened historically:

1. The bump PR still gets opened — even a totally broken bump — labeled
   `needs-fixup`, with the failure point (image build, version regen, or
   full validation) and any logs called out in the PR body.
2. A human (or an agent) fixes forward on the **same branch**
   (`pins/bump-<old>-<new>`): adjust `package.mask`/`package.unmask` entries
   in the `Dockerfile`, tweak `configs/overlay/**` ebuilds, or hand-edit a
   lock entry, then commit directly to that branch.
3. **`build.yml` does not auto-trigger on pushes to arbitrary branches** —
   it only triggers on push to `master`, tags, `workflow_dispatch`, and
   schedule. So after pushing a fixup commit, re-run validation manually:
   `gh workflow run build.yml --ref pins/bump-<old>-<new>` (or the Actions
   UI "Run workflow" button, selecting that branch).
4. Repeat until green, then merge the PR normally. Nothing in this pipeline
   merges on your behalf.

## Caveat: `savedconfig` changes require a binpkg purge

`build.yml` restores per-package binary packages (`.gpkg.tar`) from
`s3://<bucket>/packages/<BUILD_EPOCH>/` and builds with `--usepkg`
(`scripts/build-packages.sh`). Portage's binpkg reuse keys on **version + USE
flags + CHOST** — it does **not** hash `savedconfig` contents. So editing a
`savedconfig`-governed package's config **without bumping its version** yields a
binpkg Portage treats as identical to the cached one, and the **stale binary
(built with the old config) is silently reused** — the config change never takes
effect in the built image.

Packages this affects in this repo:

| Package | Config file |
| --- | --- |
| `sys-apps/busybox` | `configs/portage/savedconfig/sys-apps/busybox` (applet set, e.g. `CONFIG_FINDFS`) |
| `sys-kernel/monolith-kernel` | `configs/kernel.config` |

**When you change one of these configs, purge its cached binpkg for the current
epoch before the next build** (or the change is a no-op):

```sh
# Targeted purge (recommended) — busybox:
aws s3 rm --recursive "s3://<bucket>/packages/<BUILD_EPOCH>/sys-apps/busybox/"
# Kernel:
aws s3 rm --recursive "s3://<bucket>/packages/<BUILD_EPOCH>/sys-kernel/monolith-kernel/"
```

Bumping the package version (or `BUILD_EPOCH`, which changes the whole cache
path) also invalidates it naturally. A durable fix would be to opt
`savedconfig` packages out of binpkg reuse (`emerge --usepkg-exclude`) or to key
the cache on a config hash — tracked as a follow-up. (`busybox` is cheap to
rebuild every time; the kernel is not, which is why this is a purge-on-change
rule rather than an unconditional rebuild.)

> Real example: the `CONFIG_FINDFS=y` change that makes the `persist` feature's
> primary label lookup work will **not** take effect until the cached busybox
> binpkg for the current epoch is purged. (The init script's superblock-scan
> fallback keeps `persist` working regardless, but the `findfs` path stays
> absent until the rebuild.)
