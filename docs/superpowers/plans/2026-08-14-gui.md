# The Monolith GUI (SP-GUI) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development to implement task-by-task. Steps use `- [ ]`.

**Goal:** A bitmap-only X GUI (dwm + st + dmenu) that runs identically on a 486DX2/8MB and a modern laptop — static, framebuffer-native, zero-dlopen.

**Architecture:** kdrive **Xfbdev** server over the existing vesafb (no DRM), driving a minimal client stack (xorg-proto + libxcb + libX11 + libXext, nothing else). All suckless clients de-Xft'd via ::gentoo `USE=savedconfig` + pinned noxft patches. `startx` is a tiny house shell script; nothing draws at boot. CI proves it via a QEMU `gui` boot-test variant that screendumps and golden-compares.

**Tech Stack:** overlay ebuild `x11-base/monolith-xserver` (lane TBD by G1 recon); ::gentoo x11 libs + dwm/st/dmenu (savedconfig) + font-misc-misc/terminus-font; QEMU screendump + PPM golden compare.

## Global Constraints (from spec §0, §2, §7 — verbatim values)
- ZERO dlopen on the disc. Full Xorg is DISQUALIFIED (it dlopens drivers). X server must be kdrive/TinyX static.
- NO Xft, NO fontconfig, NO freetype ANYWHERE in v1 (hard line). Bitmap core fonts only: `fixed` (misc-misc) + terminus (PCF).
- Client libs in v1: `x11-base/xorg-proto`, `libxcb` (+xcb-proto), `libX11`, `libXext` — AND NOTHING ELSE. No Xt/Xaw/Xmu/ICE/SM.
- Everything cross+static under `configs/portage/env/static.conf`; every source Manifest-pinned; overlay ebuild edits revbump (S3 binpkg cache — see memory `overlay-ebuild-revbump-busts-binpkg-cache`).
- Overlay ebuilds need a `<cat>/<pkg> **` line in `configs/portage/package.accept_keywords/i486`.
- Hand-authored rootfs files (startx, .xinitrc) go into `app-misc/monolith-base` (owned, not allowlisted — see memory `rootfs-files-unowned-attestation`), NOT hand-installed by build-rootfs.sh.
- No display manager, no compositor, no autostart-X, no second GUI stack — ever.
- Honor vesafb's mode (800x600x8); Xfbdev inherits the fb, no modesetting of our own.
- Ground truth (2026-08-14): INPUT_MOUSEDEV=y, MOUSE_PS2=m, SERIO_SERPORT=y (already built-in), KEYBOARD_ATKBD=y, FB_VESA=y, DRM off, gpm in world.

### G1: X-server lane decision + bare Xfbdev boot (RESEARCH-GATED — the pivot)

**Interfaces produced (G2+ consume these):** a working, static, no-dlopen `x11-base/monolith-xserver` providing `Xfbdev` that boots on vesafb; the chosen lane (A/B/C) and its pin (source URL/version + configure line + patches).

- [x] **Step 1: Recon — DONE (2026-08-14).** → **LANE A chosen: `tinycorelinux/tinyx`** (github.com/tinycorelinux/tinyx, pin commit `feab72c`, 2024-11-13). Evidence (`.batteries/reports/gui-xserver-recon.md`): zero `dlopen` in the whole tree; `kdrive/fbdev/fbdev.c` drives `/dev/fb0` via ioctls (inherits vesafb, no modesetting); LIVING (Tiny Core Linux 16.2 ships Xfbdev.tcz ~350KB from this tree); musl build fix already merged (issue #3); bitmap-only by design (no xkb/xinput/GL). Lane B (xorg-server-1.19.6, last tag with working `--enable-xfbdev`) = documented fallback. Lane C (Xvesa) = same tree, `--enable-xvesa`.
- [x] **Step 2: Author `x11-base/monolith-xserver` (Lane A) — DONE, CI-GREEN 2026-08-14 (build 31797792285; PR #42; commit ee8d787; Failed:0 + boot-test + attestation all green; `/usr/bin/Xfbdev` on the ISO, static i486).** Took 3 CI builds. **The second fight — server reuses CLIENT headers + GCC-14 strictness (see memory [[tinyx-xfbdev-static-build-recipe]]):** tinyx (2007 kdrive) `#include`s headers ::gentoo ships only in libX11/libXext/libXau/libXdmcp. Owner chose the LEAN path (keep the client stack OUT). A tree-wide header-gap enumeration bounded it to **5 self-contained shims** vendored into `files/` + staged in src_prepare (all sub-includes resolve from xorg-proto; server provides the impls → no client lib links): `extensions/{XShm,sync}.h` (libXext), `extensions/XTest.h` (server-mode STUB — dodges the libXi/XInput.h chain), `Xauth.h` (libXau; xauembed.c is the embedded impl), `Xdmcp.h` (libXdmcp; XDMCP off + `#ifdef HASXDMAUTH` → header-only). `Xpoll.h` is free (xorg-proto generates+installs it). Plus `flag-o-matic append-flags -Wno-error={implicit-int,implicit-function-declaration,int-conversion,incompatible-pointer-types}` for GCC-14. Overlay ebuild `x11-base/monolith-xserver-1.3_p20241113` (upstream `AC_INIT([tinyx], 1.3)` + commit date). **Correction to the recon note:** the rl144 precedent is *GitHub's per-commit archive tarball, Manifest-pinned* — NOT S3 vendoring (S3 is only the documented fallback if GitHub's gzip drifts). So `SRC_URI=".../tinyx/archive/feab72c….tar.gz -> ${P}.tar.gz"`, Manifest pinned (BLAKE2B+SHA512, bytes fetched + hashed locally). tinyx ships only `configure.ac`+`autogen.sh` → `inherit autotools` + `eautoreconf` (BDEPEND `virtual/pkgconfig x11-misc/util-macros`; configure.ac uses 16 XORG_* macros). `econf --enable-kdrive --disable-xvesa --enable-xfbdev --disable-install-setuid --disable-{xdmcp,xdm-auth-1,xres,screensaver,dbe,xf86bigfont,dpms,werror}` (static via env/static.conf). Ships `/usr/bin/Xfbdev`; src_install readelf-asserts static+i386. **The first real fight — libXfont v1:** tinyx's `configure.ac` hardcodes pkg-config `xfont` (v1 API), but ::gentoo dropped `x11-libs/libXfont` and ships only the incompatible `libXfont2` (`xfont2`). tinyx's own README anticipates this ("can't find libXfont ver 1 → x.org/archive"). So authored a **second overlay ebuild `x11-libs/libXfont-1.5.4`** (last v1 release; x.org release tarball ships `./configure`, `econf --disable-freetype --enable-pcfformat --enable-bdfformat --disable-snfformat` → bitmap-only, no freetype). DEPEND (from configure.ac ground truth): server ← `xorg-proto xtrans libXfont libfontenc sys-libs/zlib`; **NO pixman** (recon guessed it; tinyx's 1.2.0-era fb doesn't PKG_CHECK it). Both `**` in accept_keywords; both pinned in versions.lock; only the server is a world member (libXfont pulled as its DEPEND).
- [ ] **Step 3: Bare-boot proof (TDD gate before any client) — NEXT.** Two blockers found while planning it: (a) **xsetroot needs libX11** — which the lean G1 server deliberately lacks. Instead, screendump the server's OWN output: a freshly-started X server with no client paints the default **gray root stipple + X-shaped cursor** — distinctly not-black — proving the server drew to the framebuffer, needing NO client. (b) **X opens a default `fixed`+`cursor` font at startup**; we ship no fonts until G3. Options: build `x11-libs/libXfont` with `--enable-builtins` (gzipped PCF baked into `.text` → fontless server start — the TinyX way, and it serves G3 too), OR pull `media-fonts/font-misc-misc`+`font-cursor-misc` forward. **Lean-aligned pick: `--enable-builtins`** (verify libXfont 1.5.4 ships the builtin BDF + that `--enable-builtins` works standalone). Then a scoped `gui` boot-test variant (`-vga std`, ≥32MB): boot → `Xfbdev :0 -fbdev /dev/fb0 &` → settle → QEMU monitor `screendump` (PPM) → assert not-uniformly-black. (Full golden bar+st lands in G3.)

### G3: dwm + dmenu + fonts + startx + CI variant — the real desktop

Land the `gui` boot-test variant (32MB, -vga std) with the bar+st golden compare + in-guest `xdpyinfo` exit-0. Deliverable: `startx` → dwm bar + st, CI-gated.
